## 1. Goal and constraints

5.0 is the breaking major. It carries:

- every dependency and toolchain update (Flutter/Dart floor, AGP/Gradle/Kotlin model, Java target, minSdk, iOS minimum, Media3, Pigeon, lints);
- every public API break (section 4);
- one behaviour contract for Android and iOS (section 5);
- the native rework that contract needs (section 6);
- a public native API on both platforms so any native surface in the host app (CarPlay, Android Auto, custom Kotlin or Swift UI) can drive the same player, with the plugin storing nothing (section 6.3).

Constraints (decided, not reopened):

- Pigeon over platform channels. No FFI/JNI interop. Pigeon's native-interop mode rejects event channels, so state keeps flowing through one Pigeon event channel.
- 4.2 ships first, from `4.x`, and is merged forward into `master`. Fixes never flow backwards.
- No code comments in new code (maintainer rule). Commit messages are one line, no attribution footer.
- Anything 4.2 owns is a prerequisite here, not a work item.

### 1.1 Assumed 4.2 content

Taken from `docs/plans/4.2.md` (branch `4.x`, section 4) as of the reconcile commit. Expected on `master` after the merge-forward:

Platform-interface types (4.2):

```dart
enum PlaybackStatus { idle, loading, playing, paused, error }

enum RadioPlayerErrorCode {
  invalidSource, network, httpStatus, unsupportedFormat,
  backgroundRestricted, timeout, unknown,
}

class RadioPlayerError {
  const RadioPlayerError({required this.code, required this.message});
  final RadioPlayerErrorCode code;
  final String message;
}

class RadioPlayerState {
  const RadioPlayerState({
    this.status = PlaybackStatus.idle,
    this.currentIndex,
    this.currentSource,
    this.nowPlaying,
    this.volume = 0.5,
    this.error,
  });
}
```

In 4.2 only some error codes are emitted; the rest are reserved. 5.0 starts emitting all of them.

- `FlutterRadioPlayerPlatform` has a synchronous `RadioPlayerState get state` and `Stream<RadioPlayerState> get stateStream` (throwing defaults). Caching and replay live in each Dart platform implementation (android, ios). `currentSource` is resolved in Dart from the list passed to `initialize`. There is no `getState()` on the Dart platform interface.
- App-facing: `static final FlutterRadioPlayer instance = FlutterRadioPlayer();`, `state`, `stateStream`. The public constructor and the three legacy streams remain. The legacy streams are cached single streams derived from state, keep per-platform semantics, do not replay, drop consecutive duplicates and are not `@Deprecated`.
- Pigeon 26.1.7 in both platform packages: `PlaybackStatusMessage` enum, `RadioPlayerErrorMessage`, `RadioPlayerStateMessage { status, currentIndex, nowPlayingTitle, volume, error }`, host call `getState()`, event `onStateChanged()`. The three legacy event channels are already deleted natively.
- Android: state lives in a process-wide store (5.0 replaces it with per-engine state, N-A1/N-A2); calls before `initialize()` are no-ops; the notification tap opens the launcher activity (`getLaunchIntentForPackage`); `state.volume` defaults to 0.5.
- No native unit tests exist; `4.x` CI is pinned to Flutter 3.47.0.
- Lifecycle fixes B1-B7: lazy symmetric setup/teardown, no audio session at launch (iOS), no static `sessionActivity` (Android), artwork fix, interruption-resume fix.
- F2 (`play()` re-prepares) and Android becoming-noisy pause.
- Local path overrides for the platform packages (T1), CI jobs that compile the example, T3/T4 fixes, examples reading state.

If the shipped 4.2 deviates from this, update sections 4 and 6 before starting.

Two forward-looking statements in the 4.2 plan no longer hold for 5.0: calls with no sources do not become a `StateError` (they stay no-ops, G10), and `RadioPlayerError` does not gain `sourceId` or `willRetry` (G7). Neither statement appears in 4.2's README, changelogs or dartdoc on `origin/4.x` (checked by grep, 2026-11-12), so nothing published needs correcting.

## 4. Public API for 5.0

Design goals, in priority order:

1. The common radio app (one station or a station list, a play/pause button, a now-playing line) needs one object, one widget and no boilerplate.
2. One player per process, said plainly. Nothing to construct and nothing to dispose.
3. Calls are safe in any order and straight from UI callbacks. Commands apply in call order, awaited or not. With nothing to act on they do nothing. When a command's future completes, `state` already reflects it.
4. Fewer knobs with good defaults over many options. Every option must have a default that suits a typical radio app.
5. Anything 4.2 shipped as the migration bridge (`instance`, `state`, `stateStream`, the `RadioPlayerState` field names, the `PlaybackStatus` and `RadioPlayerErrorCode` value sets) keeps its name and meaning. Apps that adopt them on 4.2 migrate once. Everything else may change.
6. Only invalid arguments throw (an index outside the list, a NaN volume). Playback problems, including a bad URL in a station list from a backend, show up in `state`.

### 4.0 Quick start (target README snippet)

```dart
await player.setSources(const [
  RadioSource(url: 'https://example.com/chill.mp3', title: 'Chillout'),
  RadioSource(url: 'https://example.com/jazz.aac', title: 'Jazz FM'),

RadioPlayerBuilder(

        onPressed: player.playOrPause,
      ),
      for (final (index, source) in state.sources.indexed)
        ListTile(
          title: Text(source.title ?? source.url),
          selected: index == state.currentIndex,
          onTap: () => player.play(index: index),
        ),
    ],
  ),
);
```

Single station:

```dart

  RadioSource(url: 'https://example.com/live.mp3', title: 'My Radio'),
```

### 4.1 Dart surface

App-facing package `flutter_radio_player`:

```dart
class FlutterRadioPlayer implements ValueListenable<RadioPlayerState> {
  static final FlutterRadioPlayer instance;

  RadioPlayerState get state;
  Stream<RadioPlayerState> get stateStream;

  @override
  RadioPlayerState get value;
  @override
  void addListener(VoidCallback listener);
  @override
  void removeListener(VoidCallback listener);

  Future<void> setSources(
    List<RadioSource> sources, {
    int? initialIndex,
    bool autoPlay = false,
  });
  Future<void> setOptions(RadioPlayerOptions options);

  Future<void> play({int? index});
  Future<void> pause();
  Future<void> playOrPause();
  Future<void> stop();
  Future<void> next();
  Future<void> previous();
  Future<void> setVolume(double volume);
}

class RadioPlayerBuilder extends StatefulWidget {
  const RadioPlayerBuilder({
    super.key,
    required this.builder,
    this.buildWhen,
  });
  final Widget Function(BuildContext context, RadioPlayerState state) builder;
  final bool Function(RadioPlayerState previous, RadioPlayerState current)?
      buildWhen;
}
```

`FlutterRadioPlayer` has no public constructor. There is no `dispose()`, no `selectSource()` and no `options` getter (reasons below and in section 10, G3, G7, G9).

Method semantics:

| Method | Does |
|---|---|
| `setSources(sources, {initialIndex, autoPlay})` | Replaces the source list. Safe on every app start and whenever the list is refreshed: a station that is playing keeps playing if it is still in the list (selection rules below). Opens no connection unless playback is requested. `setSources([])` stops playback and leaves the player with no sources (`idle`). Does not change volume or options. |
| `setOptions(options)` | Replaces the options of the shared player. Takes effect at once, at any time, before or after `setSources`. |
| `play()` | Plays the current source. Connects if the stream is not loaded (never played, stopped, failed, or paused for more than 30 s), so playback starts at live audio. Clears a pending error. Does nothing if already playing or loading. |
| `play(index: i)` | Makes source `i` current and plays it. This is the "station tapped" call. Same as `play()` when `i` is already current. |
| `pause()` | Pauses. Lock-screen and notification controls stay and show play. Cancels a reconnect in progress. |
| `playOrPause()` | `pause()` if playback is requested (`state.isPlaying`), otherwise `play()`. Decided natively, so it never acts on a stale `state`. |
| `stop()` | Turns the radio off: stops playback, closes the stream, removes the notification and lock-screen info, gives up the audio session (iOS) and the foreground service (Android). Keeps sources, `currentIndex`, volume and options. `play()` starts it again. |
| `next()` / `previous()` | Moves one source and keeps the play state: playing stays playing on the new source, not playing stays not playing. Wraps at the ends if `options.wrapAround`, otherwise does nothing there. Does nothing with fewer than two sources. |
| `setVolume(v)` | Player volume, not device volume. Clamped to 0.0-1.0. |

`setSources` selection rules:

1. `initialIndex` given: that source becomes current.
2. `initialIndex` omitted: the current source stays current if the new list contains a source with the same `id`, and `currentIndex` follows it (the same index if that entry matches, otherwise the first match). If there is no match, the first source becomes current.
3. If the current source after the call has the same `id`, `url` and `headers` as before the call, the stream is left alone: playback, `status`, `nowPlaying` and `error` do not change, and a changed `title` or `artwork` updates the lock screen and notification in place. Otherwise the old stream is closed, `nowPlaying` and `error` clear and `status` becomes `paused`.
4. Then `autoPlay: true` acts like `play()`. `autoPlay: false` does nothing more; it does not pause.

Rules for every command:

- Order. Commands are applied in the order they were called, awaited or not. `player.setSources(list); player.play(index: 2);` plays source 2.
- Completion. The returned future completes after the native player has applied the command and `state` has been updated from the native reply. After `await player.setSources(list)`, `player.state.sources` is `list`. After `await player.play()` with a source to play, `player.state.isPlaying` is `true`, unless the request failed at once and `state.error` says why. Outcomes that take time (audio becoming audible, a later failure) arrive through `state`.
- Nothing to act on. With no sources, `play()`, `pause()`, `playOrPause()`, `stop()`, `next()` and `previous()` do nothing and complete normally. Buttons can be wired to them before the list has loaded.
- Errors. A command throws only for an invalid argument, always through the returned future, and a rejected call changes nothing:
  - `RangeError`: `initialIndex` outside the list passed to the same `setSources` call; `index` in `play(index:)` negative, or not below the number of sources the native player holds when the call is applied.
  - `ArgumentError`: `setVolume(double.nan)`.
- Nothing in Dart is checked against the cached `state`. The cache fills asynchronously, so such a check could reject a correct call. The native player is the only judge of "is this index in the list".
- No command completes with a `PlatformException`. A native failure (the service cannot start, the stream fails) is reported in `state.error`.

One source-switch rule for every path: `next` and `previous`, from Dart and from lock-screen or notification buttons, keep the play state. `play(index:)` is the one call that switches and starts. "Play state" means whether playback is requested: `state.isPlaying` in Dart, the play intent (`playWhenReady`) natively. This replaces the 4.x platform split (Android kept the play state, iOS auto-played), the `autoPlayOnSelect` option from the first draft of this plan and `selectSource()` from the second (G3).

`FlutterRadioPlayer` is a `ValueListenable<RadioPlayerState>`, the same contract `VideoPlayerController` and `CameraController` offer through `ValueNotifier`. `value` is `state`. Listeners are called once per distinct state, at the same moment `stateStream` emits. So the player works directly with `ValueListenableBuilder`, `ListenableBuilder`, `AnimatedBuilder`, `Listenable.merge` and Provider's `ListenableProvider`, with no wrapper (Riverpod and Bloc users can wrap `stateStream` with a `StreamProvider` or a stream subscription):

```dart
ValueListenableBuilder(
  valueListenable: FlutterRadioPlayer.instance,
  builder: (context, state, _) => Text(state.nowPlaying?.title ?? ''),
);
```

It implements `ValueListenable`, not `ChangeNotifier`/`ValueNotifier`: there is no public setter for `value` and no `dispose()` (the player is never disposed; section 4.1 ownership). Adding the first listener subscribes to the platform state stream exactly as listening to `stateStream` does. Removing the last listener does not tear anything down, so widget rebuilds never reconnect native channels.

`RadioPlayerBuilder` is a thin convenience over this listenable. It adds `buildWhen` and needs no `valueListenable:` argument. It listens to `FlutterRadioPlayer.instance`, starts from `state` (never a blank first frame) and rebuilds on every distinct state, or only when `buildWhen` returns `true` if it is given. State changes are rare (status changes, a new ICY title every few minutes, volume while a slider is dragged), so most apps need no `buildWhen`.

Ownership and lifetime (applies to sections 5, 6 and 7):

- There is one native player per process. Every engine that uses the plugin controls the same player and sees the same state. Sources, current source, play state, volume and options are all shared.
- The first command from any engine creates the native player. Reading `state` or `value`, listening to `stateStream`, adding a listener and building a `RadioPlayerBuilder` or `ValueListenableBuilder` attach to a player that already exists, but never create one.
- There is no `dispose()`. `stop()` turns the radio off; `setSources([])` also forgets the list. A widget's `dispose()` has nothing to call. An engine going away (Activity destroyed, background engine finished) drops only that engine's listener; playback continues.
- The native player ends with the process. On Android it also ends when the service stops: no engine attached and nothing playing, or the task removed with `stopOnTaskRemoved`. The next command creates a fresh player: no sources, volume 1.0, default options.
- Restarted Dart code meets a running player. After a hot restart, or when Android recreates the Activity while audio plays in the background, the first snapshot shows the real state, and startup code that calls `setSources` again does not interrupt playback (selection rule 2).
- Commands from another engine are ordinary commands: `stop()` from engine B stops what engine A plays. `setOptions` from engine B replaces the shared options; an engine that never calls `setOptions` changes none.

Semantics pinned here (the table in section 5 repeats them per platform):

- `state` is synchronous and always valid. Before the first native snapshot it is idle, with no sources and volume 1.0.
- `stateStream` is one cached broadcast stream. Each new listener first receives `state`, then every change. It never emits two equal states in a row.
- Invariants, on both platforms:
  - `status == idle` exactly when `sources` is empty, and then `currentIndex` is `null`. With sources, `currentIndex` is never `null`.
  - `status == error` implies `error != null`.
  - `error != null` implies `status` is `error` (gave up) or `loading` (reconnecting).
- Status meanings, unchanged from 4.2:
  - `idle`: no sources.
  - `paused`: sources set, playback not requested. This covers never started, paused and stopped. It also covers playback held back by the system (interruption, transient audio-focus loss).
  - `loading`: playback requested, not audible yet (connecting, buffering, stalled, reconnecting).
  - `playing`: audible.
  - `error`: failed and not retrying. `play()` retries. 4.2 never retried, so there every pending error meant `status == error`; in 5.0 a pending error while the player retries is `loading` (`isReconnecting`).
- Getters:
  - `isPlaying` is `status == playing || status == loading`: playback is requested. Use it for the play/pause button; it does not flip while the stream buffers. This is the meaning `playing` has in just_audio and audio_service and `isPlaying` has in video_player. For "audible right now", compare `status == PlaybackStatus.playing`.
  - `isLoading` is `status == loading`. Use it for a spinner.
  - `isReconnecting` is `status == loading && error != null`: the stream failed and the player is retrying; `error` says why.
  - `currentSource` is `sources[currentIndex]`, or `null` when there are no sources.
- `state.sources` is the list the native player holds, echoed back in every state message. Every engine therefore sees the real list, even when another engine set it. The plugin is meant for lists of up to a few hundred sources (V18).
- `RadioSource`:
  - `id` defaults to `url`. The plugin uses it to recognise the current source across `setSources` calls. Apps use it to map a source back to their own data. Duplicate ids are allowed; the first match wins.
  - `url` is not validated in Dart. A source whose URL is not an absolute `http` or `https` URL stays in the list and fails with `invalidSource` when it is played. One bad row from a backend never rejects the whole list.
  - `headers` are sent with the stream request (mechanism per platform: N-A9, N-I6). `toString` prints header names only, so tokens do not end up in logs.
  - `artwork` is an `http(s)` URL or a Flutter asset path, as in 4.x.
- `NowPlayingInfo`:
  - `title` is the raw ICY `StreamTitle`, unchanged from 4.x except that it is no longer nullable: `state.nowPlaying` itself is `null` when there is no title.
  - `state.nowPlaying` is `null` until the stream delivers a non-empty title for the current source, and `null` again after a source change and after `stop()`. It never holds the station title.
  - `artist` and `song` are getters that split `title` at the first `" - "` and trim both sides. Both are `null` if there is no separator or either side is empty. This is best effort: stations format the title as they like.
- Errors and reconnect:
  - `RadioPlayerError` is unchanged from 4.2. It always concerns the current source.
  - A retryable failure (`network`, `timeout`, `httpStatus` 5xx, `unknown`) starts a reconnect: `status` is `loading` and `error` stays set. The backoff is fixed: 1 s doubling to 30 s.
  - The only knob is how long to keep trying (`giveUpAfter`, default 5 minutes; `ReconnectPolicy.none` never retries). It is clamped to 9 minutes on Android (section 6, N-A6). After that `status` is `error`.
  - A failure that retrying cannot fix (`invalidSource`, `unsupportedFormat`, `backgroundRestricted`, `httpStatus` 4xx) sets `status = error` at once.
  - `error` clears when audio becomes audible, and on `play`, `pause`, `stop` or a change of current source.
- Options:
  - Options belong to the shared player. They change only through `setOptions`, which replaces all of them. `setSources` never touches them.
  - `AndroidOptions.notificationIcon` is the drawable or mipmap resource name of the notification small icon. All `AndroidOptions` fields are ignored on iOS. There are no iOS-only options in 5.0.
- Exports: `FlutterRadioPlayer`, `RadioPlayerBuilder`, `RadioSource`, `NowPlayingInfo`, `RadioPlayerState`, `PlaybackStatus`, `RadioPlayerError`, `RadioPlayerErrorCode`, `RadioPlayerOptions`, `ReconnectPolicy`, `AndroidOptions`. `VolumeInfo` is removed. `package:flutter_radio_player/testing.dart` exports `FakeRadioPlayer`.

Changes relative to 4.2's types. Code that reads them keeps compiling:

- `RadioPlayerState`: adds `sources`, `isPlaying`, `isLoading` and `isReconnecting`. `currentSource` becomes a getter with the same meaning; code that constructs a `RadioPlayerState` (tests) passes `sources` instead of `currentSource`. The `volume` default changes from 0.5 to 1.0.
- `RadioPlayerError`: no change. All `RadioPlayerErrorCode` values are now emitted.
- `NowPlayingInfo.title`: `String?` becomes `String`.

### 4.2 Platform interface

```dart
abstract class FlutterRadioPlayerPlatform extends PlatformInterface {
  Stream<RadioPlayerState> get stateStream;

  Future<RadioPlayerState> setSources(
    List<RadioSource> sources, {
    int? initialIndex,
    bool autoPlay = false,
  });
  Future<RadioPlayerState> setOptions(RadioPlayerOptions options);
  Future<RadioPlayerState> play({int? index});
  Future<RadioPlayerState> pause();
  Future<RadioPlayerState> playOrPause();
  Future<RadioPlayerState> stop();
  Future<RadioPlayerState> next();
  Future<RadioPlayerState> previous();
  Future<RadioPlayerState> setVolume(double volume);
}
```

- Every command returns the state as it is after the command was applied. The app-facing class stores it before completing its own future. This is what makes the completion rule of section 4.1 hold without depending on how an event-channel message and a method reply are interleaved.
- `stateStream` emits the native snapshot once the listener is attached, then every change. It may emit duplicates.
- Natives send snapshots in the order they were produced, events and replies alike. Dart applies them in arrival order.
- The app-facing class and the platform packages send the host call synchronously, before their first `await`, so the order of unawaited calls is the order on the channel. The app-facing class subscribes to `stateStream` on the first use of any member, before it sends a command.
- The app-facing class (`packages/flutter_radio_player/lib/flutter_radio_player.dart`) owns the singleton, the cached `state`, replay and deduplication, the argument checks that need no player state (`initialIndex` against the list passed in, a negative index, NaN, the volume clamp), `RadioPlayerBuilder` and the testing fake.
- The platform packages map messages to models and map the native `invalid_index` error to `RangeError`. Nothing else. They are identical apart from class name.
- Removed:
  - the 4.2 synchronous `state` getter;
  - `getState()`, both on the platform interface and as a Pigeon host call (the snapshot sent on listen and the command replies replace it);
  - `dispose`;
  - legacy `isPlayingStream`, `nowPlayingStream`, `volumeStream`, `getVolume`, `initialize`, `nextSource`, `previousSource`, `jumpToSourceAtIndex`, and the code in the platform packages that derives the legacy streams from state.
- The platform interface bumps to 5.0.0; the android and ios implementations require `^5.0.0` of it.

Pigeon schema (both packages):

- `RadioPlayerStateMessage` becomes `{ status, sources: List<RadioSourceMessage>, currentIndex, nowPlayingTitle, volume, error }`.
- `RadioSourceMessage` gains `id` and `headers`.
- `RadioPlayerErrorMessage` and `PlaybackStatusMessage` are unchanged from 4.2.
- New `RadioPlayerOptionsMessage`, sent by `setOptions` only.
- Host API: `setSources(sources, initialIndex, autoPlay)`, `setOptions(options)`, `play(index)`, `pause()`, `playOrPause()`, `stop()`, `next()`, `previous()`, `setVolume(volume)`. Each returns `RadioPlayerStateMessage`. The only error a host call returns is `invalid_index`.
- Event API: `onStateChanged()` stays.

### 6.1 Android

#### N-A1. Controller listener replaces static sinks

- Problem: at `dd53cd6` the service holds `PigeonEventSink`s in its companion object (`Service:34-36`) and the plugin copies its sinks into them (`AndroidPlugin:62-66`, `:72-76`, `:219-255`). 4.2 replaces the three sinks with one state event but keeps a process-wide Android state store; that store is what this item replaces (re-locate by symbol after the merge). Pigeon types leak into the service (`Service:22-24`); a second engine's `onListen` overwrites the first's sink; the service wraps every emit in `mainHandler.post` (`Service:86-119`).
- Change:
  - The plugin attaches a `Player.Listener` to its `MediaController` (a `Player`). One `StateHolder` (pure Kotlin, no Android types) folds `onPlaybackStateChanged`, `onPlayWhenReadyChanged`, `onIsPlayingChanged`, `onMediaItemTransition`, `onMediaMetadataChanged`, `onVolumeChanged`, `onPlayerErrorChanged` and session-extras changes into one `RadioPlayerStateMessage` and emits it on the single state event channel.
  - The service no longer imports any Pigeon type; delete `playbackStateSink`, `nowPlayingSink`, `volumeSink` and the three listener bodies that emit.
  - Controller callbacks arrive on the application looper, so the `Handler(Looper.getMainLooper()).post` wrapper goes away. Verify this (V15), because the `PigeonEventSink` must be called on the main thread.
  - The state message carries the full source list (section 4.1), `url` and `headers` included, to every engine. Requirement: `url` and `headers` never travel in `MediaMetadata` or its extras, because other apps' media controllers and notification listeners can read session metadata. `MediaItem`s in the session carry only a `mediaId`, the title and the artwork. The plugin hands `url` and `headers` to the service with the command that sets the list (`onAddMediaItems` request metadata, stripped before the items reach the player, or a custom command), and the service keeps the full list. Mechanism for handing it to the other engines, to be settled by V17, in order of preference: (1) session extras set per controller, for same-package controllers only, or a `radio.getSources` custom command, with a list revision so that `StateHolder` emits only when its timeline and its list agree; (2) an in-process local binder to the service's list. The engine that called `setSources` already has the list and does not wait for the echo.
  - Every host call replies with the `StateHolder` snapshot taken after the command was applied (section 4.2, row 25). `MediaController` applies player commands to its local state at once (masking), so the snapshot is available synchronously; verify for each command used (V15). Commands whose outcome is decided in the service (`next`/`previous` at a list end, `setOptions`, the list replacement of N-A11, a reload on resume) reply only after the controller has received the service's result. During one host call `StateHolder` emits at most one event, after the last controller call and before the reply.
  - Host calls made while the controller is still connecting are queued and applied in call order (the 4.2 L1 rule, kept).
  - On `onListen`: if no service is running, the plugin emits the default idle snapshot at once and does not start the service (row 16; use an in-process liveness flag set in `PlaybackService.onCreate`/`onDestroy`, the one process-wide value allowed). If a service is running, the plugin connects its controller and emits the snapshot once connected. This replaces the 4.2 `getState()` host call.
- Acceptance: `grep -rn "PigeonEventSink" .../core/` returns nothing and no process-wide state store remains (no `companion object` / top-level `object` holding state other than the liveness flag); two engines both receive each state change (C11); a command's reply reflects the command (C12); `adb shell dumpsys media_session` shows no stream URL and no header value for the session; unit tests of `StateHolder` pass on the JVM.

#### N-A2. Per-engine state, shared reference-counted player

- Problem: at `dd53cd6` plugin and service state is global (companion `sessionActivity` `AndroidPlugin:38-47`, sinks above); after 4.2 it is a process-wide store with the launcher-intent session activity. Flutter's plugin guidance is to assume multiple engines and keep state per plugin instance.
- Change:
  - Each `FlutterRadioPlayerPlugin` instance owns: its `MediaController` (built on the first host call, or on listen when a service is already running, N-A1), its `StateHolder`, its event sink. It caches no options and no volume.
  - The player, the session, the source list, the volume and the options live in `PlaybackService` and are shared. The service's lifecycle follows controller count: the service stops itself when no controller is connected and there is no play intent (use `onUpdateNotification`/`onTaskRemoved` hooks plus the session's `connectedControllers`); it keeps playing with zero connected controllers while the user listens (background playback survives the Activity and engine being destroyed). A new engine attaches its listener and receives the current snapshot on `onListen`.
  - Ownership follows section 4.1. There is no `dispose()` host call. `stop()` calls `player.stop()` (items kept), the service leaves the foreground and the notification goes; `setSources([])` also clears the items. Every attached engine sees the result. An engine detach (`onDetachedFromEngine`) releases only that plugin's `MediaController` and sink; playback continues. If the service goes away under an attached engine (controller `onDisconnected`), the plugin emits the default idle snapshot and connects again on the next command. Release the controller from a task posted to the main looper, never from inside a listener callback (T4 note).
  - `sessionActivity` is already gone in 4.2 (launcher intent via `packageManager.getLaunchIntentForPackage(packageName)`); keep that. The change here is moving the process-wide state store into per-engine `StateHolder`s.
- Acceptance: instantiate the plugin twice in a unit/instrumented test with separate `StateHolder`s; destroy the Activity while playing: audio continues, and a new engine reports `playing` with the full source list without calling any command; headless engine registration and a state listener alone do not start the service (C11, C10).

#### N-A3. Metadata single owner

- Problem: three writers feed the title today. The service emits `IcyInfo` titles from `onMetadata` (`Service:101-112`), emits the static title from `onMediaMetadataChanged` (`Service:114-120`), and the notification reads session metadata that never receives the ICY title when the `MediaItem` has a preset title (known gotcha; `buildMediaItem` sets `setTitle`, `AndroidPlugin:262-267`). Result: Dart and the notification can disagree (row 6). `latestMetadata` is written six times (`AndroidPlugin:100,135,141,148`; `Service:108,115`) and never read; 4.2 removes it.
- Change: the service is the only component that interprets ICY. It writes the ICY title into the session's metadata so that the notification, any other controller and the Dart state read one value. Candidate mechanisms, to be chosen by spike S4 (V4), in order of preference:
  1. Wrap the `ExoPlayer` in a `ForwardingPlayer` whose `getMediaMetadata()` returns the item metadata with the ICY title overlaid, and notify listeners of the change.
  2. `replaceMediaItem` on the current item with updated `MediaMetadata` (ExoPlayer can update a progressive/ICY item without re-preparing when only metadata changes; verify, a re-buffer is a failure).
  3. `MediaSession.setSessionExtras` plus a custom notification provider reading the extras.

- Change (cont.): station title moves to artist/subtitle per row 6; the static title is never reported as `nowPlaying`.
- Acceptance: with a stream carrying ICY, the notification title, `MediaController.mediaMetadata.title` and `state.nowPlaying.title` are equal within one state emission; after a source switch, all three clear (C6).

#### N-A4. Policy: wrap-around, kept play state and index defence for lock-screen and Dart alike

- Problem: next/previous from the notification run natively (Media3 handles `COMMAND_SEEK_TO_NEXT`), so policy cannot live in Dart.

#### N-A5. Options and custom commands

#### N-A6. Reconnect with backoff bounded by Android 17 rules

- Problem: no error handler (`Service:84-122` has no `onPlayerError`); after an error, `play()` does nothing (F2). Android 17 hardens background audio for all apps: background playback, audio focus and volume calls need a visible activity or a non-short foreground service, and fail silently otherwise (checked 2026-11-12, V6).
- Change (in the service, so it works with no Dart engine alive):
  - `Player.Listener.onPlayerError` classifies `PlaybackException` into `RadioPlayerErrorCode`. If the code is retryable (row 10) and `giveUpAfter` is not zero (`ReconnectPolicy.none`), it schedules `player.prepare()` + play with the fixed backoff (1 s doubling to 30 s), via `Handler` on the main looper, and publishes `status = loading` with the error set. Otherwise it publishes `status = error` at once.
  - `pause()`, `stop()` and a change of current source cancel the schedule and clear the error (row 18).
  - Stop retrying after `min(giveUpAfter, 9 minutes)`: then `player.stop()`, publish `status = error`, let the foreground service demote. Resume only on explicit `play()` (which also re-prepares, row 11). The 9 minute cap is deliberately under the brief's "drops under 10 minutes" guidance until V6 settles the exact rule.
  - Never start the foreground service from the background: retry only while the service is already foreground; user-initiated `play()` arrives from a visible Activity or a media button.
  - Handle `ForegroundServiceStartNotAllowedException` where playback is started from the plugin side (map to `backgroundRestricted`).
  - The pure parts (`ReconnectScheduler`: next delay, give-up decision with an injected clock) live in plain Kotlin for JVM tests.
- Acceptance: JVM test of the scheduler sequence (1, 2, 4, ... capped, stop at the budget); on device, cut the network for 30 s: `loading` with `error` set, then `playing` with `error` cleared; cut for 12 min: `error`, service no longer foreground; a 404 goes to `error` with no retry; run the dropped-network test with `adb shell cmd audio set-enable-hardening throw` and confirm no `SecurityException`/silent failure (C8).

### 6.3 Native API and car support (G2, G13, G14)

Rules for the whole section: the plugin stores nothing (no preferences, no files, no database). A host that wants playback to survive a cold start saves what it needs from `state` / `stateStream` and gives it back through the restore hook. Every car feature is off until the host opts in. Opening a browse tree or connecting a car never starts audio.

#### N-C0. Public native API on a Flutter-free core

- Goal (maintainer, 2026-11-18): a developer writing a native surface (a CarPlay scene, an Android Auto or custom Kotlin UI) wires into our native player and plays anything, while the plugin does the heavy lifting.
- Change: both platforms get a public native API with the same commands and state as the Dart API (`setSources`, `setOptions`, `play(index:)`, `pause`, `playOrPause`, `stop`, `next`, `previous`, `setVolume`, observe state), in the plugin's own public types (never the Pigeon `*Message` classes). The core (state, policies, reconnect, metadata, source selection) imports no Flutter symbols; the Flutter plugin class is a thin adapter that maps Pigeon calls to the core. The same rules as the Dart API apply (command order, no-ops with no sources, only invalid arguments throw).
- Scope (G14): same process as the Flutter engine, shipped inside the existing plugin packages. Native code in the host app (CarPlay scene delegate, Android Auto, custom UI) reaches the one shared player. Separate-process targets (a watchOS app, Wear OS, Android Automotive OS) would run their own player; they need the core as a standalone artifact (later) and a remote-control channel for controlling the phone's player, which the host builds.
- Acceptance: the example's native code (Kotlin Android Auto hook, Swift CarPlay delegate) compiles against the public API only; a lint or CI check fails if the core files import Flutter; V25.

#### N-C1. Android Auto: export, trust and manifest

- Problem: the service is `exported="false"` (`AndroidManifest.xml:9`), has no `MediaButtonReceiver`, and its `MediaLibrarySession.Callback` implements no browse methods (`PlaybackService.kt:67`).
- Change: export the service; in `onConnectAsync` accept our own app's controller as today and external controllers only when the host opted in with a manifest meta-data entry owned by the plugin (name fixed at implementation time, set by the host in its `AndroidManifest.xml`); reject the rest. Ship `res/xml/automotive_app_desc.xml` with `<uses name="media"/>` and declare `com.google.android.gms.car.application` only when the host opts in (the host's manifest carries the meta-data entry, so apps that do not opt in do not claim Auto support). Declare `androidx.media3.session.MediaButtonReceiver` so a head-unit or headset Play press reaches the service.
- Acceptance: merged example manifest with the opt-in lists the service once, exported; without it an external controller (second test app) is refused; Android Auto's Desktop Head Unit lists the app.

#### N-C2. Android Auto: browse tree, playback and resume

- Change: `onGetLibraryRoot` returns a browsable root; `onGetChildren` returns one playable `MediaItem` per source (`mediaId` = `RadioSource.id`, title, artwork URI); `onSetMediaItems` / `onAddMediaItems` map a tapped `mediaId` back to the source and call the same path as `play(index:)`. The tree is flat, so the queue is always the full source list with the tapped index current (react-native-track-player makes the tapped item's siblings the queue; this is equivalent). `onPlaybackResumption` restores the list and current index from the restore hook, and prepares without starting unless the request is an explicit play (media button, Auto play). Restore only for the app's own controller and for explicit resume requests, never on service start or on an Auto browse.
- Restore hook (Kotlin): `interface RadioPlayerRestoreProvider { fun restore(context: Context): RestoredPlayer? }` where `RestoredPlayer` holds the sources and the current index. The host registers it in `Application.onCreate()` through a static registrar. It runs on the service's main thread and must return quickly from local data; the plugin does not wait on network. With no provider registered the tree is empty and resumption does nothing. `RestoredPlayer` and the source type it holds are the plugin's own public Kotlin types; the Pigeon-generated `*Message` classes are never part of this API.
- Artwork: Auto may not render http artwork URIs (reported, not confirmed); see V21.
- Acceptance: a JVM test asserts the `MediaItem` list built for the browse tree matches the sources in the Pigeon state message for the same core state; DHU browses and plays a source with the app process killed and a provider registered; with no provider the app opens, the tree is empty and nothing plays; a headset power-on does not start playback (V22).

#### N-C3. CarPlay bridge (iOS), on the N-C0 API

- Change: the iOS side of N-C0, usable from a host scene delegate without Flutter: read the current sources and state, observe changes, call play by index, pause, next and previous. It operates on the same shared core as the Dart API (N-I1), so Dart and the car see the same player. The bridge has its own public Swift types (`RadioPlayerSnapshot`, `RadioSourceInfo`, `RestoredPlayer`); the Pigeon-generated `*Message` classes stay internal, so a Pigeon upgrade never breaks host car code. The core builds one snapshot per state change and maps it once to both outputs (the Pigeon event and the bridge observers). Bridge observers are called on the main thread. The existing `MPNowPlayingInfoCenter` and remote commands (N-I2, N-I3) feed `CPNowPlayingTemplate`.
- Restore hook (Swift): `protocol RadioPlayerRestoreProvider { func restore() -> RestoredPlayer? }`, registered by the host in the app or scene delegate before the scene connects. Same rules as Android: no storage in the plugin, fast, no auto-play.
- The plugin does not ship the entitlement, `Info.plist` scene configuration or template UI (G13 A).
- Acceptance: a unit test asserts that, for the same core state, the bridge snapshot and the Pigeon state message carry equal values (status, sources, current index, now playing, volume, error); the app starts without a window and the CarPlay scene connects with the phone UI closed (the react-native-track-player docs describe this as the CarPlay cold-start path); the example's scene delegate lists the sources in a `CPListTemplate`, plays a tapped station and shows the Now Playing template, in the CarPlay simulator with the entitlement; the CarPlay launch works with the phone UI closed.

#### N-C4. Docs, example and host checklist

- README "Cars" section: the Android Auto manifest opt-in, the restore provider on both platforms with a small SharedPreferences / UserDefaults recipe fed by `stateStream`, the CarPlay steps (entitlement request to Apple, `Info.plist` scene configuration, the scene delegate), and what the plugin does not do.
- `example/` implements the recipe on both platforms (host-side persistence with `shared_preferences` and a native read of it is a V23 decision).
- Acceptance: a new app follows the section and reaches a working head-unit simulator session without reading plugin source.

Alternative: `StateError` backed by an optimistic Dart mirror and a command queue: more machinery, and still wrong when another engine changes the list. | As proposed. |
| G11 | `setSources` on a live player; connect on demand | **Closed (accepted by the maintainer, 2026-11-12).** With `initialIndex` omitted `setSources` keeps the current source by `id`, and it never interrupts an unchanged stream (row 22). Nothing connects before a play request (row 23). This makes startup code safe on Activity recreation, hot restart, a second engine and a list refresh, and avoids a notification and data use before the first play. Alternatives: always reset to index 0 and stop (4.x; a relaunch restarts or kills background audio); pre-buffer on `setSources` (4.x; a faster first play). Cost: N-A11, N-I8, V19. | As proposed. |
| G12 | Resume after a long pause | **Closed (accepted by the maintainer, 2026-11-12).** `play()` after more than 30 s paused reloads the stream and resumes live; shorter pauses resume from the buffer (row 24). Fixed constant, no option. Alternatives: always reload (simplest; a 1-2 s re-buffer after every pause); never reload (platform default; stale audio, then a drop when the buffer runs out, and the two platforms differ). | 30 s. Confirm after V20 shows what each platform does today. |

## 12. Pre-release and release checklist

### 12.1 Pre-releases

Publish `5.0.0-dev.N` to pub.dev for testers; each bumps all four packages.

- [ ] `5.0.0-dev.1` after P0+P1+P2 (toolchain, Media3, Pigeon, merged 4.2): proves the new floor in real apps; behaviour unchanged except build requirements.
