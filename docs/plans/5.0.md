## 1. Goal and constraints

5.0 is the breaking major. It carries:

- every dependency and toolchain update (Flutter/Dart floor, AGP/Gradle/Kotlin model, Java target, minSdk, iOS minimum, Media3, Pigeon, lints);
- every public API break (section 4);
- one behaviour contract for Android and iOS (section 5);
- the native rework that contract needs (section 6).

Constraints (decided, not reopened):

- Pigeon over platform channels. No FFI/JNI interop. Pigeon's native-interop mode rejects event channels, so state keeps flowing through one Pigeon event channel.
- 4.2 ships first, from `4.x`, and is merged forward into `master`. Fixes never flow backwards.
- No code comments in new code (maintainer rule). Commit messages are one line, no attribution footer.
- Anything 4.2 owns is a prerequisite here, not a work item.

### 1.1 Assumed 4.2 content

Taken from `docs/plans/4.2.md` (branch `4.x`, section 4) as of the reconcile commit. Expected on `master` after the merge-forward:

Platform-interface types (4.2):

```dart
enum PlaybackStatus { idle, loading, playing, paused, error }

enum RadioPlayerErrorCode {
  invalidSource, network, httpStatus, unsupportedFormat,
  backgroundRestricted, timeout, unknown,
}

class RadioPlayerError {
  const RadioPlayerError({required this.code, required this.message});
  final RadioPlayerErrorCode code;
  final String message;
}

class RadioPlayerState {
  const RadioPlayerState({
    this.status = PlaybackStatus.idle,
    this.currentIndex,
    this.currentSource,
    this.nowPlaying,
    this.volume = 0.5,
    this.error,
  });
}
```

In 4.2 only some error codes are emitted; the rest are reserved. 5.0 starts emitting all of them.

- `FlutterRadioPlayerPlatform` has a synchronous `RadioPlayerState get state` and `Stream<RadioPlayerState> get stateStream` (throwing defaults). Caching and replay live in each Dart platform implementation (android, ios). `currentSource` is resolved in Dart from the list passed to `initialize`. There is no `getState()` on the Dart platform interface.
- App-facing: `static final FlutterRadioPlayer instance = FlutterRadioPlayer();`, `state`, `stateStream`. The public constructor and the three legacy streams remain. The legacy streams are cached single streams derived from state, keep per-platform semantics, do not replay, drop consecutive duplicates and are not `@Deprecated`.
- Pigeon 26.1.7 in both platform packages: `PlaybackStatusMessage` enum, `RadioPlayerErrorMessage`, `RadioPlayerStateMessage { status, currentIndex, nowPlayingTitle, volume, error }`, host call `getState()`, event `onStateChanged()`. The three legacy event channels are already deleted natively.
- Android: state lives in a process-wide store (5.0 replaces it with per-engine state, N-A1/N-A2); calls before `initialize()` are no-ops; the notification tap opens the launcher activity (`getLaunchIntentForPackage`); `state.volume` defaults to 0.5.
- No native unit tests exist; `4.x` CI is pinned to Flutter 3.47.0.
- Lifecycle fixes B1-B7: lazy symmetric setup/teardown, no audio session at launch (iOS), no static `sessionActivity` (Android), artwork fix, interruption-resume fix.
- F2 (`play()` re-prepares) and Android becoming-noisy pause.
- Local path overrides for the platform packages (T1), CI jobs that compile the example, T3/T4 fixes, examples reading state.

If the shipped 4.2 deviates from this, update sections 4 and 6 before starting.

## 4. Public API for 5.0

### 4.1 Dart surface after the breaks

App-facing package `flutter_radio_player`:

```dart
class FlutterRadioPlayer {
  static final FlutterRadioPlayer instance;

  RadioPlayerState get state;
  Stream<RadioPlayerState> get stateStream;

  Future<void> setSources(
    List<RadioSource> sources, {
    int startIndex = 0,
    bool autoPlay = false,
    RadioPlayerOptions options = const RadioPlayerOptions(),
  });
  Future<void> updateOptions(RadioPlayerOptions options);

  Future<void> play();
  Future<void> pause();
  Future<void> playOrPause();
  Future<void> stop();
  Future<void> next();
  Future<void> previous();
  Future<void> selectSource(int index);
  Future<void> setVolume(double volume);
  Future<void> dispose();
}
```

- No public constructor. Tests use an `@visibleForTesting` named constructor taking a platform.
- `stateStream` is one cached broadcast stream: replays the latest state to each new listener, then emits changes. `state` is synchronous and always valid (initial: idle, volume 1.0, no sources).
- `setSources` is the only entry that creates native resources. `dispose()` tears down exactly what it built; `setSources` after `dispose()` rebuilds (cycles indefinitely).
- `setSources([])` clears sources and returns the player to idle.
- Exports: `RadioSource`, `NowPlayingInfo`, `RadioPlayerState`, `PlaybackStatus`, `RadioPlayerError`, `RadioPlayerErrorCode`, `RadioPlayerOptions`, `ReconnectPolicy`, `AndroidOptions`. `VolumeInfo` is no longer exported.

Models (platform interface, re-exported):

```dart
enum PlaybackStatus { idle, loading, playing, paused, error }

class RadioPlayerState {
  final PlaybackStatus status;
  final int? currentIndex;
  final RadioSource? currentSource;
  final int sourceCount;
  final NowPlayingInfo? nowPlaying;
  final double volume;
  final RadioPlayerError? error;

  bool get isPlaying;
  bool get isActive;
}

class RadioSource {
  const RadioSource({
    required this.url,
    String? id,
    this.title,
    this.artwork,
    this.headers = const {},
  });
  final String id;
  final String url;
  final String? title;
  final String? artwork;
  final Map<String, String> headers;
}

class NowPlayingInfo {
  final String? title;
  final String? artist;
  final String? track;
}

enum RadioPlayerErrorCode {
  invalidSource, network, httpStatus, unsupportedFormat,
  backgroundRestricted, timeout, unknown,
}

class RadioPlayerError {
  final RadioPlayerErrorCode code;
  final String message;
  final String? sourceId;
  final bool willRetry;
}

class RadioPlayerOptions {
  const RadioPlayerOptions({
    this.wrapAround = true,
    this.autoPlayOnSelect = true,
    this.reconnect = const ReconnectPolicy(),
    this.android = const AndroidOptions(),
  });
}

class ReconnectPolicy {
  const ReconnectPolicy({
    this.enabled = true,
    this.initialDelay = const Duration(seconds: 1),

  });
}
```

Semantics pinned here (the table in section 5 repeats them per platform):

- `RadioSource.id` defaults to `url`. Ids must be unique within one `setSources` call. `headers` are applied to the stream request (mechanism per platform: N-A9, N-I8).
- Relative to 4.2's `RadioPlayerState`: additive `sourceCount`, `isPlaying`, `isActive`; `volume` default changes 0.5 -> 1.0. `currentIndex`, `currentSource`, `nowPlaying`, `status`, `error` keep their 4.2 meaning. `sourceCount` is needed so Dart can validate `selectSource` when another engine or a lock-screen action changed the sources. Decision G7 covers the additions.
- Relative to 4.2's `RadioPlayerError`: `code` and `message` unchanged; additive `sourceId` (nullable) and `willRetry` (default `false`). All `RadioPlayerErrorCode` values are now emitted.
- `currentSource` is resolved in the app-facing class by id from the list passed to `setSources` (moved there from the platform implementations). The Pigeon state message therefore carries `currentSourceId`. If the id is not in this engine's list (sources set by another engine), `currentSource` is `null` while `currentIndex` and `sourceCount` stay valid (see V17).
- `isPlaying` is `status == playing`. `isActive` is `status == playing || status == loading` (use it for the pause/play button; this replaces iOS's old "playing while buffering").
- `NowPlayingInfo.title` is the raw ICY `StreamTitle`. `artist` and `track` come from splitting `title` at the first `" - "`; both are `null` if there is no separator or either side is empty. Parsing happens once, in the platform interface, not natively.
- `RadioPlayerError.willRetry` is `true` while reconnect is scheduled. While reconnecting, `status` is `loading` and `error` stays set (with `willRetry: true`). `error` clears when `status` becomes `playing`, or on the next user action.
- Dart-side validation, before any platform call (section 5, rows 4, 8, 9): `RangeError` for index and volume, `ArgumentError` for duplicate ids and non-`http(s)` URLs, `StateError` if a transport call needs sources and `sourceCount == 0`.
- `ReconnectPolicy.giveUpAfter` is clamped to 9 minutes on Android (section 6, N-A6).
- `AndroidOptions` fields are ignored on iOS. There are no iOS-only options in 5.0.

### 4.2 Platform interface

Starting point is 4.2's interface (synchronous `state` getter and `stateStream`, caching in each platform package, legacy methods still present). `FlutterRadioPlayerPlatform` becomes the same method set as the app-facing class, minus caching:

- `setSources(sources, {startIndex, autoPlay, options})`, `updateOptions`, `play`, `pause`, `playOrPause`, `stop`, `next`, `previous`, `selectSource`, `setVolume`, `dispose`, `getState()`, `Stream<RadioPlayerState> get stateStream`.
- The legacy `isPlayingStream`, `nowPlayingStream`, `volumeStream`, `getVolume`, `initialize`, `nextSource`, `previousSource`, `jumpToSourceAtIndex` are removed.
- The synchronous `state` getter is removed from the platform interface and the platform packages; `getState()` (a `Future<RadioPlayerState>`, backed by the existing Pigeon `getState()` host call) replaces it. `stateStream` stays but no longer replays.
- Caching, replay, `currentSource` resolution, validation and artist/track parsing live in the app-facing class (`packages/flutter_radio_player/lib/flutter_radio_player.dart`), so both platform packages stay thin and identical apart from class name. The platform packages no longer derive legacy streams from state; that code is deleted with the legacy streams.
- Platform interface bumps to 5.0.0; android/ios implementations require `^5.0.0` of it.

## 6. Native architecture work

Format per item: problem (with `path:line`), change, acceptance. Paths are shortened: `AndroidPlugin` = `packages/flutter_radio_player_android/android/src/main/kotlin/me/sithiramunasinghe/flutter/flutter_radio_player/FlutterRadioPlayerPlugin.kt`; `Service` = `.../core/PlaybackService.kt` in the same directory; `IosPlugin` = `packages/flutter_radio_player_ios/ios/flutter_radio_player_ios/Sources/flutter_radio_player_ios/FlutterRadioPlayerPlugin.swift`; `IosService` = `.../core/RadioPlayerService.swift`.

### 6.1 Android

#### N-A1. Controller listener replaces static sinks

- Problem: at `dd53cd6` the service holds `PigeonEventSink`s in its companion object (`Service:34-36`) and the plugin copies its sinks into them (`AndroidPlugin:62-66`, `:72-76`, `:219-255`). 4.2 replaces the three sinks with one state event but keeps a process-wide Android state store; that store is what this item replaces (re-locate by symbol after the merge). Pigeon types leak into the service (`Service:22-24`); a second engine's `onListen` overwrites the first's sink; the service wraps every emit in `mainHandler.post` (`Service:86-119`).
- Change:
  - The plugin attaches a `Player.Listener` to its `MediaController` (a `Player`). One `StateHolder` (pure Kotlin, no Android types) folds `onPlaybackStateChanged`, `onPlayWhenReadyChanged`, `onIsPlayingChanged`, `onMediaItemTransition`, `onMediaMetadataChanged`, `onVolumeChanged`, `onPlayerErrorChanged` and session-extras changes into one `RadioPlayerStateMessage` and emits it on the single state event channel.
  - The service no longer imports any Pigeon type; delete `playbackStateSink`, `nowPlayingSink`, `volumeSink` and the three listener bodies that emit.
  - Controller callbacks arrive on the application looper, so the `Handler(Looper.getMainLooper()).post` wrapper goes away. Verify this (V15), because the `PigeonEventSink` must be called on the main thread.
- Acceptance: `grep -rn "PigeonEventSink" .../core/` returns nothing and no process-wide state store remains (no `companion object` / top-level `object` holding state); two engines both receive each state change (C11); unit tests of `StateHolder` pass on the JVM.

#### N-A2. Per-engine state, shared reference-counted player

- Problem: at `dd53cd6` plugin and service state is global (companion `sessionActivity` `AndroidPlugin:38-47`, sinks above); after 4.2 it is a process-wide store with the launcher-intent session activity. Flutter's plugin guidance is to assume multiple engines and keep state per plugin instance.
- Change:
  - Each `FlutterRadioPlayerPlugin` instance owns: its `MediaController` (built on first host call), its `StateHolder`, its event sink, its options cache.
  - The player and session live in `PlaybackService` and are shared. The service's lifecycle follows controller count: the service stops itself when no controller is connected and there is no play intent (use `onUpdateNotification`/`onTaskRemoved` hooks plus the session's `connectedControllers`); it keeps playing with zero connected controllers while the user listens (background playback survives the Activity and engine being destroyed). A new engine reattaches via `getState()` (4.2) and sees the true state.
  - `dispose()` releases only that plugin's controller and, if it was the last one and `stop()` semantics apply, stops the service. Whether `dispose()` always stops playback (current `AndroidPlugin:153-159` does) or only releases the attachment is Decision G9; default in this plan: `dispose()` stops playback and releases (matches 4.1 and the iOS code), a plain engine detach does not.
  - `sessionActivity` is already gone in 4.2 (launcher intent via `packageManager.getLaunchIntentForPackage(packageName)`); keep that. The change here is moving the process-wide state store into per-engine `StateHolder`s.
- Acceptance: instantiate the plugin twice in a unit/instrumented test with separate `StateHolder`s; destroy the Activity while playing: audio continues, new engine reports `playing`; headless engine registration does not start the service (C11, C10).

#### N-A3. Metadata single owner

- Problem: three writers feed the title today. The service emits `IcyInfo` titles from `onMetadata` (`Service:101-112`), emits the static title from `onMediaMetadataChanged` (`Service:114-120`), and the notification reads session metadata that never receives the ICY title when the `MediaItem` has a preset title (known gotcha; `buildMediaItem` sets `setTitle`, `AndroidPlugin:262-267`). Result: Dart and the notification can disagree (row 6). `latestMetadata` is written six times (`AndroidPlugin:100,135,141,148`; `Service:108,115`) and never read; 4.2 removes it.
- Change: the service is the only component that interprets ICY. It writes the ICY title into the session's metadata so that the notification, any other controller and the Dart state read one value. Candidate mechanisms, to be chosen by spike S4 (V4), in order of preference:
  1. Wrap the `ExoPlayer` in a `ForwardingPlayer` whose `getMediaMetadata()` returns the item metadata with the ICY title overlaid, and notify listeners of the change.
  2. `replaceMediaItem` on the current item with updated `MediaMetadata` (ExoPlayer can update a progressive/ICY item without re-preparing when only metadata changes; verify, a re-buffer is a failure).
  3. `MediaSession.setSessionExtras` plus a custom notification provider reading the extras.
  The `MediaController` side must not need `onMetadata` (timed metadata is not reliably forwarded to controllers; V15).
- Change (cont.): station title moves to artist/subtitle per row 6; the static title is never reported as `nowPlaying`.
- Acceptance: with a stream carrying ICY, the notification title, `MediaController.mediaMetadata.title` and `state.nowPlaying.title` are equal within one state emission; after `selectSource`, all three clear (C6).

#### N-A4. Policy: wrap-around and auto-play for lock-screen and Dart alike

- Problem: next/previous from the notification run natively (Media3 handles `COMMAND_SEEK_TO_NEXT`), so policy cannot live in Dart.
- Change: the service's player is a `ForwardingPlayer` (also used by N-A3) that implements `seekToNext`/`seekToPrevious`/`seekToNextMediaItem`/`seekToPreviousMediaItem`/`seekToDefaultPosition(index)` by applying `wrapAround` (set `repeatMode = REPEAT_MODE_ALL` when true so the next/previous commands stay available at the ends; V8) and `autoPlayOnSelect` (set `playWhenReady = true` before the seek). Options reach the service by a custom `SessionCommand` registered in `onConnectAsync` (N-A5).
- Acceptance: C3 and C4 pass on Android; notification buttons behave like Dart calls.

#### N-A5. Options and custom commands

- Change: add `SessionCommand("radio.setOptions")` carrying a `Bundle` (wrap, autoPlay, reconnect fields, stopOnTaskRemoved, icon name). `MediaLibrarySession.Callback.onConnectAsync` grants it to trusted controllers only. The plugin sends it from `setSources`/`updateOptions` through `controller.sendCustomCommand`. Options are held in memory in the service; process death loses the player too, so no persistence.
- Replaces the `onAddMediaItems`-only callback at `Service:67-75` (keep `onAddMediaItems`).
- Acceptance: unit test that options Bundle round-trips; changing `wrapAround` while playing takes effect without re-preparing.

#### N-A6. Reconnect with backoff bounded by Android 17 rules

- Problem: no error handler (`Service:84-122` has no `onPlayerError`); after an error, `play()` does nothing (F2). Android 17 hardens background audio for all apps: background playback, audio focus and volume calls need a visible activity or a non-short foreground service, and fail silently otherwise (checked 2026-11-12, V6).
- Change (in the service, so it works with no Dart engine alive):
  - `Player.Listener.onPlayerError` classifies `PlaybackException` into `RadioPlayerErrorCode` and, if `options.reconnect.enabled`, schedules `player.prepare()` + play with exponential backoff (`initialDelay` doubling to `maxDelay`), via `Handler` on the main looper.
  - Stop retrying after `min(giveUpAfter, 9 minutes)`: then `player.stop()`, publish `status = error`, `willRetry = false`, let the foreground service demote. Resume only on explicit `play()` (which also re-prepares, row 11). The 9 minute cap is deliberately under the brief's "drops under 10 minutes" guidance until V6 settles the exact rule.
  - Never start the foreground service from the background: retry only while the service is already foreground; user-initiated `play()` arrives from a visible Activity or a media button.
  - Handle `ForegroundServiceStartNotAllowedException` where playback is started from the plugin side (map to `backgroundRestricted`).
  - The pure parts (`ReconnectScheduler`: next delay, give-up decision with an injected clock) live in plain Kotlin for JVM tests.
- Acceptance: JVM test of the scheduler sequence (1, 2, 4, ... capped, stop at the budget); on device, cut the network for 30 s: `loading` with `willRetry` then `playing`; cut for 12 min: `error`, `willRetry = false`, service no longer foreground; run the dropped-network test with `adb shell cmd audio set-enable-hardening throw` and confirm no `SecurityException`/silent failure (C8).

#### N-A7. Wake mode and permission

- Problem: no wake lock on the player (`Service:63-65` builds `ExoPlayer.Builder(this).setAudioAttributes(...)` only); screen-off streaming can stall on aggressive Wi-Fi power-save. The manifest has no `WAKE_LOCK` (`AndroidManifest.xml:2-3`).
- Change: `.setWakeMode(C.WAKE_MODE_NETWORK)` on the builder; add `<uses-permission android:name="android.permission.WAKE_LOCK" />` to the plugin manifest (merged into the host app, so list it in the README's permissions section and the migration guide). Becoming-noisy handling (`setHandleAudioBecomingNoisy(true)`) comes from 4.2; do not duplicate.
- Acceptance: merged manifest of the example contains `WAKE_LOCK`; `adb shell dumpsys power` shows a `*media*`/Exo wake lock while playing and none after pause/stop.

#### N-A8. Task removed

- Problem: `Service:53-57` always calls `stopSelf()` when a player exists.
- Change: honour `options.android.stopOnTaskRemoved` (default `true`). When `false`, return without stopping and let the notification keep the service in the foreground; when `true`, stop playback and the service. Guard against being called while the player is already idle.
- Acceptance: with `false`, swipe the app from recents while playing: audio continues; with `true`: stops and the notification disappears.

#### N-A9. Notification small icon and per-source headers

- Icon problem: `Service:79-82` sets the small icon from `appInfo.icon`, the launcher icon (typically a colour icon that renders as a white square).
- Icon change: resolve `options.android.notificationSmallIcon` via `resources.getIdentifier(name, "drawable", packageName)` then `"mipmap"`; fall back to a monochrome `ic_radio_notification` vector bundled in the plugin's `res/drawable`. Apply on options change by replacing the notification provider.
- Headers problem: `buildMediaItem` (`AndroidPlugin:260-285`) has no way to carry per-source HTTP headers.
- Headers change: build the player with `DefaultMediaSourceFactory(context, ResolvingDataSource.Factory(DefaultHttpDataSource.Factory(), resolver))` where the resolver adds headers by looking up the request URI (or a `MediaItem.mediaId`-keyed map) held by the service. Needs `media3-datasource` (T4). Mechanism unverified (V5); fall back to `DefaultHttpDataSource.Factory.setDefaultRequestProperties` if headers can be global per `setSources` call (document the limitation if so).
- Acceptance: a local test server logs the custom header on the stream request for each source; notification uses the named drawable; unknown name uses the bundled icon.

#### N-A10. Manifest and export surface

- `AndroidManifest.xml:9` keeps `exported="false"` unless G2 chooses Android Auto. Remove the `android.media.browse.MediaBrowserService` filter (`:13`) if the service stays unexported (it advertises browse support that is not implemented).
- Acceptance: merged manifest of the example contains the service once, unexported.

### 6.2 iOS

#### N-I1. Per-engine plugin state over a shared, reference-counted core

- Problem: `RadioPlayerService.instance` is a singleton built at plugin registration (`IosService:8,23-32`; `IosPlugin:5,9`). Each of the three stream wrappers writes its sink onto that shared object (`IosPlugin:83-118`), so a second engine overwrites the first engine's sinks. There is no `detachFromEngine`.
- Change:
  - Split `RadioPlayerService` into `RadioPlayerCore` (AVPlayer, audio session, remote commands, now-playing publisher; shared, created lazily on first `acquire`) and per-engine `FlutterRadioPlayerPlugin` instances that hold: a sink, a `StateHolder` subscription, options cache.
  - `register(with:)` creates no core (no audio session, no `AVPlayer`, no remote commands: B5). The first host call acquires it; `detachFromEngine(for:)` releases the plugin's subscription; the last release with no play intent tears the core down.
  - Replace the three stream wrappers with one state `StreamHandler` that, on `onListen`, emits the current snapshot.
- Acceptance: two plugin instances (unit test with fake messengers) both receive state; launching the app does not touch `AVAudioSession` (check by `AVAudioSession.sharedInstance().isOtherAudioPlaying` staying true on launch while music plays elsewhere) (C11, C10).

#### N-I2. Lazy audio session and symmetric remote commands

- Problem: `setupAudioSession()` and `setupRemoteCommands()` run in `init` (`IosService:25-26`, `:141-162`); `dispose()` removes the remote targets (`:129-132`) but `initialize()` never re-adds them, and `observePlayerState()` runs only from `init` (`:29`, `:217`). 4.2 fixes B1-B5 on the existing structure.
- Change: one `activate()` that sets category, activates the session, registers remote commands and observers; one `deactivate()` that is its exact inverse. `play`/`setSources(autoPlay)` call `activate()`; `stop`/`dispose`/last release call `deactivate()` (`setActive(false, options: .notifyOthersOnDeactivation)`). Remote commands: `nextTrackCommand`/`previousTrackCommand` enabled per `wrapAround` and current index (row 1). Pause/play commands read the shared play intent.
- Acceptance: `setSources` → `dispose` → `setSources` three times: lock-screen buttons work every time, state events keep flowing, other apps' audio resumes after each `dispose` (C10).

#### N-I3. Now-playing metadata single owner

- Problem: `MPNowPlayingInfoCenter.nowPlayingInfo` is written from four places: `updateNowPlayingInfo` (`:279-292`), `observePlayerState` (`:223-226`), `setNowPlayingArtwork` (`:322-327`), `dispose` (`:128`). `updateNowPlayingInfo` copies the previous artwork forward (`:286-289`) (B6), and an in-flight artwork download can land on the wrong source (`:304-312`).
- Change: one `NowPlayingPublisher` renders the whole dictionary from `RadioPlayerState` plus an artwork cache keyed by source id; nothing else writes to `MPNowPlayingInfoCenter`. Artwork loads keep their `URLSessionDataTask` and cancel it on source change; a completion applies only if its source id still matches. Title/artist follow row 6; `MPNowPlayingInfoPropertyPlaybackRate` is 1.0 only in `playing`.
- Acceptance: source A with artwork, then source B without: lock screen shows no artwork for B; switching quickly A→B→C while A's download is slow never shows A's artwork on C (C6, manual lock-screen check).

#### N-I4. Stall and failure handling, item recreation, reconnect

- Problem: only `.readyToPlay` is observed (`:196-200`); `.failed`, stalls and `failedToPlayToEndTime` are ignored (F1). An invalid URL returns silently (`:188`). A failed `AVPlayerItem` stays failed, so replaying it does nothing.
- Change:
  - Observe `AVPlayerItem.status` (`.failed` → classify `item.error`/`NSURLError`), `AVPlayerItem.playbackStalledNotification`, `AVPlayerItem.failedToPlayToEndTimeNotification`, and `AVPlayer.reasonForWaitingToPlay`, folding them into `status` (`loading` while stalled/waiting, `error` when failed).
  - Reconnect: on failure or prolonged stall, recreate the `AVPlayerItem` from the source (new `AVURLAsset`, headers re-applied) after the same backoff as N-A6, honouring `ReconnectPolicy`. The pure scheduler is shared in design (same rules) but written separately in Swift.
  - `play()` from `error`/`idle` recreates the item (row 11).
  - Invalid URL: Dart rejects first (row 9); native also publishes `error(invalidSource)` rather than returning.
  - Do not call `play()` from the interruption-end handler unless play intent was set before it began (4.2 B7; keep the stored intent in the state holder).
- Acceptance: unreachable host → `error` within the timeout with a reconnect cycle (C8); airplane-mode toggle during playback → `loading` then `playing` after restore.

#### N-I5. ICY metadata filtered by identifier

- Problem: `AVPlayerItemMetadataOutput(identifiers: nil)` (`:211`) delivers every item, and the delegate publishes the first non-empty `stringValue` of whichever item comes first (`:341-350`): could be a URL, genre or other tag.
- Change: restrict to title identifiers (candidates: `AVMetadataIdentifier.icyMetadataStreamTitle`, ID3 title, common title; settle the exact list with spike S3, V9) and ignore the rest; ignore empty strings and repeat titles. Metadata goes through the state holder, not directly to a sink.
- Acceptance: against Icecast and Shoutcast test streams and one HLS stream with timed ID3, `nowPlaying.title` equals the expected `StreamTitle` and never a URL/genre. Plain Shoutcast streams that AVFoundation does not surface remain a documented limitation (memory note: not 100% reliable).

#### N-I6. Volume default and per-source headers

- `AVPlayer.volume` default is already 1.0 on init; remove the 0.5 assignment (`:28`) and the 0.5 fallback (`:89`).
- Headers: `AVURLAsset(url:options: ["AVURLAssetHTTPHeaderFieldsKey": headers])` (key is long-standing but not in the public docs; V5). Acceptance: local server logs headers per source.

#### N-I7. Entry cleanup for `FlutterFramework`

- After T5, `import Flutter` continues to work; confirm there is no duplicate `Flutter` module in the SwiftPM build (build with SwiftPM on). No source change expected.
