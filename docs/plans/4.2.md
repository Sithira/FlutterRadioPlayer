# flutter_radio_player 4.2 release plan

Branch: `4.x` (from `master` at `dd53cd6`). Tag: `v4.2.0`. Baseline: v4.1.0.

All `path:line` references are against `dd53cd6` and were re-read for this plan. Nothing here was built or run; every behaviour claim that comes from reading code is marked "to confirm" where it matters.

## 1. Goal and constraints

4.2 fixes the lifecycle and correctness bugs found in the 4.1.0 review, surfaces playback errors, and adds a state snapshot API next to the existing API. It is a minor release: apps on 4.1.x upgrade with no code change.

Hard limits:

- [ ] No public API removed, renamed or changed in meaning. Only additions.
- [ ] No SDK-floor change: every `environment:` block stays `sdk: '>=3.4.3 <4.0.0'`, `flutter: '>=3.3.0'`; Android `minSdk` stays 21; iOS stays 14.0 (`ios/flutter_radio_player_ios.podspec:14`, `ios/flutter_radio_player_ios/Package.swift:8`).
- [ ] No dependency or toolchain bump: Pigeon stays `^26.0.0` resolving to 26.1.7; Media3 stays 1.10.0 (`android/build.gradle:52-55`); AGP 8.9.2, Kotlin 2.1.20, JVM 21, `compileSdk` 36, `flutter_lints ^3.0.0`, Mockito 5.23.0 all stay.
- [ ] No new Android permission and no manifest change in the plugin.
- [ ] The cross-platform behaviour differences (wrap-around, auto-play on switch, `isPlayingStream` while buffering, out-of-range index, `nowPlayingStream` after a switch, lock-screen title with ICY data, volume on `initialize()`) stay exactly as they are today. They are 5.0.
- [ ] No reconnect/backoff, no wake lock, no new options, no renames. All 5.0.

## 2. Branching and release flow

- [ ] `4.x` is created from `dd53cd6`. All 4.2 work happens on `4.x`, directly or via short-lived feature branches merged into `4.x`.
- [ ] `master` is not touched by 4.2 work. It carries 5.0.
- [ ] After release, `4.x` is merged forward into `master` (`git merge --no-ff 4.x`). Fixes never flow backwards.
- [ ] Later 4.x patches (4.2.1, ...) go on `4.x` first, are tagged from `4.x`, and are merged forward again.
- [ ] Before releasing, rehearse the merge-forward in a scratch worktree (`git merge --no-commit 4.x` on a copy of `master`) to see the conflicts early. Expect them in `pubspec.yaml` versions, the four changelogs, `android/build.gradle`, `Package.swift`, the podspec and the Pigeon-generated files. Resolution rule: keep `master`'s toolchain, dependency and version lines; keep `4.x`'s behaviour changes; regenerate Pigeon output on `master` after the merge rather than hand-merging `*.g.*` files.
- [ ] CI (`.github/workflows/ci.yml`, `on: [push, pull_request]`) already runs on any branch, so `4.x` needs no trigger change.

## 3. Work items

Conventions: "Check" is the acceptance check. "Manual" scenarios use `example/` on a physical Android device and a physical iPhone unless stated. Dart tests live in the existing `test/` folders.

### 3.1 Lifecycle fixes

#### L1. Android works after `dispose()` (B1, B3)

Problem:
- `MediaController` is built only in `onAttachedToEngine` (`FlutterRadioPlayerPlugin.kt:55-67`).
- `dispose()` (`:153-159`) calls `releaseController()` (`:185-201`), which sets `controllerFuture = null`; every later call, `initialize()` included, hits `notReadyError()` in `runOnController` (`:165-168`).
- Both example apps call `dispose()` in `State.dispose` and `initialize()` in `initState` (`example/lib/main.dart:56-65`, `packages/flutter_radio_player/example/lib/main.dart:49-58`), so leaving and re-entering the screen breaks the player.

Change (`FlutterRadioPlayerPlugin.kt`):
- [ ] Remove the controller construction from `onAttachedToEngine`. Keep `RadioPlayerHostApi.setUp` and `setupEventChannels` there (they are engine-scoped, not controller-scoped).
- [ ] Add `ensureController()` that builds the controller if `controllerFuture == null`, using the same token/builder code that is in `onAttachedToEngine` today. `initialize()` calls it. Calling `initialize()` twice without `dispose()` reuses the existing controller.
- [ ] The `initialize` handler calls `ensureController()` synchronously, before `runOnController`. A transport call sent right after an unawaited `initialize()` therefore attaches to the same controller future and runs after it, in order. This is a requirement: do not defer controller creation to a posted task or callback.
- [ ] `play`, `pause`, `playOrPause`, `setVolume`, `nextSource`, `previousSource`, `jumpToSourceAtIndex` with no controller (before any `initialize()`, or after `dispose()`) complete successfully as a no-op (this matches today's behaviour on an empty playlist and does not start the service) but log at warning level, naming the method, for example `play() called before initialize(); ignored` (`Log.w`, tag `FlutterRadioPlayer`). Never silent. 5.0 turns these into a `StateError`. `getVolume` with no controller returns 0.5. `dispose()` with no controller is a no-op that still resets the state store (see S3).
- [ ] `dispose()` keeps its current order (release controller, `stopService`) and resets the state store so Dart receives a final `idle` snapshot.
- [ ] Guard the race where `dispose()` runs while `buildAsync()` is still pending: `releaseController()` already cancels an unfinished future (`:196-198`); confirm a following `initialize()` builds a fresh one.

Check:
- [ ] Manual: open example, play, leave the screen and re-enter it 10 times. Playback starts each time, notification appears each time, no `controller_unavailable` in logcat. On 4.1.0 the second entry fails (reproduce first, see step 0).
- [ ] Manual: `dispose()` then `initialize(playWhenReady: true)` from a button in the example, same result.
- [ ] Manual: call `play()` before `initialize()` on a fresh process: no exception, no notification, and `adb logcat -s FlutterRadioPlayer:W` shows the warning naming `play()`. Same after `dispose()`.
- [ ] Manual: `player.initialize(sources, playWhenReady: false);` without `await`, then immediately `player.play()`: playback starts (the `initialize` and `play` calls reach the same controller in order).
- [ ] On Android `initialize()` already overwrites `playWhenReady` (`FlutterRadioPlayerPlugin.kt:98`), so an early `play()` before `initialize()` never carried over in 4.1.0; this no-op is not a regression there.

### 3.2 Failure handling

#### E1. Errors reach Dart through the state (F1)

Problem: no error path on either platform. Android has no `onPlayerError` in the listener (`PlaybackService.kt:84-122`). iOS has no `.failed` item status or stall handling and returns silently on an invalid URL (`RadioPlayerService.swift:188`). The 4.2 scope is surfacing the error, not recovering from it.

Change:
- [ ] Android: add `onPlayerError(error: PlaybackException)` to the service listener; store `RadioPlayerErrorMessage(code = <mapped code>, message = error.message ?: error.errorCodeName)` in the state store (mapping in the "Error codes" item below). Clear the error on a new `initialize()`, on `onMediaItemTransition`, on `play()`, and when `isPlaying` becomes true.
- [ ] iOS: observe `AVPlayerItem.status == .failed` (use `item.error`), and add observers for `.AVPlayerItemFailedToPlayToEndTime`. `.AVPlayerItemPlaybackStalled` maps to status `loading`, not `error`. Invalid URL (`:188`): set error code `invalidSource` and leave the current item and `currentIndex` unchanged; move the `currentIndex = index` assignment (`:185`) below the guard so the state never names a source that did not load. Clear the error on the next successful `loadSource` or `play`.
- [ ] Error codes (`RadioPlayerErrorCode`, the set 5.0 also uses). 4.2 natives emit only what they can determine: `invalidSource`, `network`, `unknown`. `httpStatus`, `unsupportedFormat`, `backgroundRestricted` and `timeout` are reserved and may never be emitted in 4.x; do not guess them.
  - Android: `PlaybackException.errorCode` in the `ERROR_CODE_IO_NETWORK_*` group (`IO_NETWORK_CONNECTION_FAILED`, `IO_NETWORK_CONNECTION_TIMEOUT`) gives `network`; `ERROR_CODE_IO_BAD_HTTP_STATUS` and anything else gives `unknown` (a status-code-aware mapping to `httpStatus` is not required in 4.2); a source whose URI cannot be parsed/opened as given (`ERROR_CODE_IO_FILE_NOT_FOUND`, `ERROR_CODE_IO_INVALID_HTTP_CONTENT_TYPE`, `ERROR_CODE_PARSING_*` are not mapped) is left as `unknown`. Keep the Media3 `errorCodeName` in `message` for diagnostics.
  - iOS: unparsable URL string gives `invalidSource`; `NSURLErrorDomain` errors from `item.error` / the failed-to-play notification with codes in the connectivity family (`notConnectedToInternet`, `networkConnectionLost`, `cannotConnectToHost`, `cannotFindHost`, `dnsLookupFailed`, `timedOut`) give `network`; everything else gives `unknown`, with the `NSError` localized description in `message`.
- [ ] No reconnect, no retry.

Check:

### 3.3 State snapshot

Design in one paragraph: each native side keeps one state object, emits the whole snapshot on every mutation, and replays the current snapshot when the Dart side starts listening. The Dart platform implementation owns exactly one subscription to that event channel, caches the latest snapshot, and exposes it as `state` and `stateStream`. The three legacy streams are derived from the same cached snapshots inside the platform implementation. The full API is in section 4.

#### S1. Android state store

- [ ] New file `core/RadioStateStore.kt` (process-wide object, same pattern as the existing companion sinks; one store per process is accepted for 4.2, per-engine state is 5.0). Holds: current `RadioPlayerStateMessage`, the event sink, `error`, and the per-platform `nowPlayingTitle`.
- [ ] The service player listener in `PlaybackService.kt` recomputes the snapshot from the `Player` in `onEvents` (playback state, `playWhenReady`, `isPlaying`, `mediaItemCount`, `currentMediaItemIndex`, `volume`) and pushes it to the store. Emit only if different from the last snapshot.
- [ ] Status mapping, evaluated in this order: `error != null` gives `error`; `mediaItemCount == 0` gives `idle`; `playWhenReady` and state in {`STATE_IDLE`, `STATE_BUFFERING`} gives `loading`; `isPlaying` gives `playing`; everything else (including READY with playback suppressed, ENDED, and not playing) gives `paused`.
- [ ] `nowPlayingTitle` keeps 4.1.0 semantics exactly, with one mutation (and one emission) per trigger, never coalesced: `onMediaItemTransition` sets `null` (`PlaybackService.kt:85-87`); `onMetadata` with a non-empty `IcyInfo.title` sets that title (`:101-112`); `onMediaMetadataChanged` with a non-null title sets it (`:114-120`). Do not move to `MediaController` callbacks in 4.2: the controller does not receive raw `onMetadata` (to confirm), and that rework is 5.0.
- [ ] Idle default (service not running, or after `dispose()`): status `idle`, no index, no title, no error, volume 0.5.
- [ ] All sink calls are posted to the main looper (the service listener already does this, `PlaybackService.kt:86`; keep it).
- [ ] The plugin's `OnStateChangedStreamHandler.onListen` registers the sink and immediately emits the current snapshot; `onCancel` clears the sink. `getState()` returns the store snapshot and does not need a controller.

Check:
- [ ] Manual: attach a `stateStream.listen(print)` and run play, pause, switch source via notification next, ICY title change, volume change, error: each produces a snapshot with the right `status`, `currentIndex`, `nowPlaying`, `volume`, `error`.

#### S2. iOS state holder

- [ ] In `RadioPlayerService.swift`, add a private `makeState()` returning `RadioPlayerStateMessage`, emitted (main queue) after: `timeControlStatus` change, `loadSource`, metadata output, `setVolume`, error set/cleared, `initialize`, `dispose`. Skip emission when equal to the last one.
- [ ] Status mapping, in order: item failed or `error` set gives `error`; no sources or no current item gives `idle`; `timeControlStatus == .waitingToPlayAtSpecifiedRate` gives `loading`; `.playing` gives `playing`; `.paused` gives `paused`.
- [ ] `nowPlayingTitle` keeps 4.1.0 semantics: `nil` on every `loadSource` (`:205-207`), the ICY title from the metadata output (`:343-347`).
- [ ] `volume` is the `AVPlayer.volume`; initial 0.5.
- [ ] `onListen` replays the current snapshot; `getState()` returns `makeState()`.
- [ ] Keep the pure mapping in a free function so it can be unit-tested later (5.0) without changing behaviour.

Check: same manual scenario as S1 on iOS.

#### S3. Dart platform implementations (both packages)

Both files are identical apart from the class name; keep them in step.

- [ ] Constructor gains optional test hooks: `FlutterRadioPlayerAndroid({@visibleForTesting RadioPlayerHostApi? hostApi, @visibleForTesting Stream<RadioPlayerStateMessage> Function()? stateEvents})`. `registerWith` is unchanged (`flutter_radio_player_android.dart:9-11`).
- [ ] One lazy native subscription, created on the first `initialize()`, `state` or `stateStream` access, held for the life of the instance (not cancelled on `dispose()`).
- [ ] `initialize()` stores `sources` in the instance (used to resolve `currentSource` from `currentIndex`); `dispose()` clears them.
- [ ] Message-to-model mapping: index out of range or null gives `currentSource: null`; `nowPlayingTitle` maps to `NowPlayingInfo(title: ...)`, or `null` when no snapshot has set one; `PlaybackStatusMessage` maps one-to-one onto `PlaybackStatus`.
- [ ] `stateStream`: single cached broadcast stream; every new listener first receives the current cached snapshot (if one has arrived), then live updates.
- [ ] Legacy streams (`isPlayingStream`, `nowPlayingStream`, `volumeStream`) become single cached broadcast streams fed from the same handler. They do not replay on listen (as today). The first snapshot after the native subscription is only a baseline and emits nothing on them; afterwards each emits only when its own field changes.
- [ ] Per-platform derivation, preserving 4.1.0 semantics:

  | Legacy stream | Android emits when | iOS emits when |
  |---|---|---|
  | `isPlayingStream` | `status == playing` changes | `(status == playing \|\| status == loading)` changes |
  | `nowPlayingStream` | `nowPlaying.title` changes (includes `null` after a switch, then the source title or ICY title) | same field, `null` after a switch, then the ICY title |
  | `volumeStream` | `volume` changes; `VolumeInfo(volume, isMuted: volume == 0)` | same |

  Known, accepted difference from 4.1.0: consecutive identical values are no longer re-emitted (for example iOS emitted `true` twice when `waiting` became `playing`; `setVolume` with the same value emitted again).
- [ ] Remove `@visibleForTesting` from the `isPlayingStream` getter (`flutter_radio_player_android.dart:53`, `flutter_radio_player_ios.dart:53`).
- [ ] Remove the three Pigeon-based getters' stream construction (`onPlaybackStateChanged()` etc.) from the Dart side.
- [ ] `state` before any snapshot has arrived is `RadioPlayerState()` (idle, volume 0.5). `state` is eventually consistent: the future from `initialize()` completes when the command is dispatched, not when the snapshot has changed. Document this and do not assert it in tests except through the stream.
- [ ] After `dispose()` completes, call `getState()` once to refresh the cache.

Check (Dart tests in each platform package, using the injected hooks):
- [ ] Message-to-state mapping for all five statuses, in-range, out-of-range and null index, with and without error, with and without title.
- [ ] Two listeners on `stateStream`; cancel one; the other keeps receiving (A1 regression).
- [ ] Late subscriber receives the latest snapshot first (A2).
- [ ] Two listeners on each legacy stream behave the same way; none replays on listen.
- [ ] First snapshot emits nothing on legacy streams; a later `loading` snapshot emits `true` on iOS and nothing on Android; a later `playing` snapshot emits `true` on both.
- [ ] A sequence `title null` then `title X` produces two `nowPlayingStream` events; a repeated `X` produces one.
- [ ] The existing delegation tests still pass untouched.

## 4. API additions

### 4.1 Platform interface (`packages/flutter_radio_player_platform_interface/lib/`)

New files under `src/types/`, exported from `types.dart`:

```dart
enum PlaybackStatus { idle, loading, playing, paused, error }

enum RadioPlayerErrorCode {
  invalidSource, network, httpStatus, unsupportedFormat,
  backgroundRestricted, timeout, unknown,
}

class RadioPlayerError {
  const RadioPlayerError({required this.code, required this.message});
  final RadioPlayerErrorCode code;
  final String message;
}

class RadioPlayerState {
  const RadioPlayerState({
    this.status = PlaybackStatus.idle,
    this.currentIndex,
    this.currentSource,
    this.nowPlaying,
    this.volume = 0.5,
    this.error,
  });
  final PlaybackStatus status;
  final int? currentIndex;
  final RadioSource? currentSource;
  final NowPlayingInfo? nowPlaying;
  final double volume;
  final RadioPlayerError? error;
}
```

`RadioPlayerErrorCode` is the final value set: 5.0 uses it unchanged and only adds optional fields (`sourceId`, `willRetry`) to `RadioPlayerError`, so the type survives the 4.x to 5.0 migration. 4.2 natives emit only the codes they can determine (at minimum `invalidSource`, `network`, `unknown`); the others are reserved and may never be emitted in 4.x. Both classes also define `==`, `hashCode` and `toString`, like the existing models. Status meanings (documented on the enum): `idle` no sources loaded or disposed; `loading` playback requested and not yet audible; `playing` audible; `paused` sources loaded, playback not requested (or suppressed); `error` a playback error is pending, cleared by the next play, source change or initialize.

Added to `FlutterRadioPlayerPlatform` (`flutter_radio_player_platform_interface.dart`), same default-throws style as the existing members:

```dart
RadioPlayerState get state { throw UnimplementedError('state has not been implemented.'); }
Stream<RadioPlayerState> get stateStream { throw UnimplementedError('stateStream has not been implemented.'); }
```

The legacy getters stay and keep their current signatures and docs.

### 4.4 Why each addition is non-breaking

- New classes, a new enum and new static/instance members: existing code cannot reference them, so it cannot break. A subclass of `FlutterRadioPlayer` that declares its own static `instance` would clash; subclassing a class with only a default constructor is not a supported pattern.
- `FlutterRadioPlayerPlatform` is an abstract class used through `extends` (it requires `PlatformInterface` token verification; only test doubles use `MockPlatformInterfaceMixin`). Third-party implementers that `extends` it inherit the throwing defaults for `state` and `stateStream` and keep compiling and working for every 4.1.0 member. Only code that calls the new members against a platform that does not implement them gets `UnimplementedError`, which is how every unimplemented member already behaves. A test double that uses `implements` plus the mixin would have to add the two members; the repo's own doubles use `extends` (`packages/flutter_radio_player/test/flutter_radio_player_test.dart:8-9`).
- The app-facing legacy members delegate to the platform's legacy getters exactly as before, so a third-party platform keeps working.
- Dependency constraints make mixed versions impossible: android and iOS 4.2.0 require `flutter_radio_player_platform_interface: ^4.2.0`; app-facing 4.2.0 requires `^4.2.0` of all three. Old platform packages with a new interface are fine (the new members are optional there).
- Pigeon schema and native changes are internal to the platform packages.
- The enums' value sets (`PlaybackStatus`, `RadioPlayerErrorCode`) are fixed for the rest of 4.x: adding a value later would break exhaustive `switch` statements in apps, so it stays a 5.0-only change. Reserving the full `RadioPlayerErrorCode` set now, including codes 4.x never emits, is what lets apps write exhaustive handling once and keep it in 5.0. `message` is non-null, so apps never need a null check; natives always supply text.
- Behaviour changes that are not API changes are listed in the changelog: legacy streams no longer emit consecutive duplicates; Android pauses on headphone unplug; Android notification tap opens the launcher activity; calls before `initialize()` or after `dispose()` are no-ops that now log a warning on both platforms (on Android they were already no-ops on an empty playlist; on iOS this is a behaviour change only if the step 0 check shows an early `play()` started audio after `initialize()` in 4.1.0). They become a `StateError` in 5.0.
